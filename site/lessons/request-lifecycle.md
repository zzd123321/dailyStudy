# 04 · 请求链路与服务端状态

你已经能运行 Java 程序、发 HTTP 请求，也能用 if、循环和方法处理输入。这一课把它们连起来。

先想三个问题：**创建笔记后刷新页面，数据还在吗？再点一次创建，会多一条吗？重启 Java 服务后，数据还在吗？**

答案取决于程序执行了什么，以及数据存在哪里。我们继续使用第 02 课的服务，亲手追踪一条笔记，不增加新框架。

## 从点击“创建”，到得到一个 ID

假设前端发出：

```http
POST /api/notes HTTP/1.1
Content-Type: application/json

{"title":"理解服务端状态"}
```

对当前程序，可以把处理过程读成一句话：**找到创建笔记的逻辑，读懂输入，检查标题，生成 ID 并保存，最后把结果发回来。**

```text
前端发请求
    ↓
服务按路径与方法找到处理逻辑
    ↓
检查正文类型 → 解析 JSON → 检查字段
    ↓
生成 ID，保存笔记
    ↓
把结果写成 JSON，返回 201
    ↓
前端读结果，更新页面
```

这些是职责，不是每个项目都必须按同一份源码结构实现。GET 查询不需要解析创建用的 JSON；未知路径会在前面就被拒绝。

### 切换场景，观察请求停在哪里

<RequestFlow />

先选择合法创建，再试 JSON 错误、空白标题、服务未启动。观察两点：**经过了哪些步骤？有没有改变数据？**

错误请求也可能走到“生成 HTTP 响应”。返回 422 或 500，说明服务发送了一个失败响应；连接失败则没有收到这个服务的 HTTP 响应。

## 服务是一直运行的程序，不是每次请求重跑 main

第 01 课的 HelloStudy 打印一句话后结束。这个服务则在 main 中启动 HttpServer，绑定 `127.0.0.1:8082`，之后继续等待请求。

```text
Maven 编译代码
    ↓
java 启动一个进程
    ↓
main 启动 HTTP 服务
    ↓
请求 A → 处理方法
请求 B → 处理方法
请求 C → 处理方法
```

所以创建完一条笔记，还能在下一次查询里读到它：同一个服务进程还在运行，保存笔记的集合也还在。

修改源码后，只刷新浏览器不会改变旧进程里的逻辑。通常要重新编译并重启程序；后续会学习框架的开发重载。

编译完成也不等于服务已经启动。`BUILD SUCCESS` 是构建结果，浏览器需要的则是一个正在监听目标端口的程序。

## 路由：同一个路径，为什么 GET 和 POST 做不同的事

“路由”就是根据请求条件，决定由哪段代码处理。在本实验中主要看方法和路径：

| 请求 | 选中的工作 |
|---|---|
| `GET /api/notes` | 查笔记列表 |
| `POST /api/notes` | 创建笔记 |
| `GET /api/notes/2` | 查 ID 为 2 的笔记 |
| `GET /api/demo/failure` | 返回模拟的 500 |

用你刚学过的 if 表示，逻辑大致如下。**这是伪代码，不是完整 Java 程序：**

```java
if (path.equals("/api/notes")) {
    if (method.equals("GET")) {
        // 查列表。
    } else if (method.equals("POST")) {
        // 解析、校验，然后创建。
    } else {
        // 返回 405：这个路径不支持该方法。
    }
} else {
    // 继续找其他路径；全都找不到才返回 404。
}
```

第 03 课的判断，在这里仍然适用。Spring Boot 会用注解表达路由；学习框架前先知道它替你组织了什么。

### 两个 404，失败的位置不同

```bash
curl -i 'http://127.0.0.1:8082/api/unknown'
curl -i 'http://127.0.0.1:8082/api/notes/999999'
```

前者没有这个接口，返回 `route_not_found`。后者找到了“按 ID 查笔记”的接口，但没有这条笔记，返回 `note_not_found`。

它们都是 404，但一个是找不到处理入口，一个是找不到数据。**只看状态码，分不清这两个原因；还要看完整地址和错误正文。**

## 把输入处理放回 HTTP，逻辑没有变

第 03 课已经把输入处理分成几件事：

| 步骤 | 终端计划器 | HTTP 创建笔记 |
|---|---|---|
| 读取 | nextLine 读文字 | 读取请求正文 |
| 解析 | 把 "4" 转成整数 | 把 JSON 文本变成可处理的数据 |
| 校验 | 天数必须 1–7 | title 必须是合格字符串 |
| 业务 | 计算小时 | 分配 ID、保存笔记 |
| 输出 | 打印结果 | 返回状态、头和正文 |

媒介不同，原则相同：**能够读懂输入，不代表允许执行操作。**

### 当前服务先检查什么，后检查什么

```text
Content-Type 是 application/json 吗？  不是 → 415
正文超过大小上限吗？                  是   → 413
能解析成一个 JSON 值吗？               不能 → 400
是对象且 title 是合格字符串吗？         不是 → 422
以上都通过 → 分配 ID → 保存 → 返回 201
```

这解释了一个容易困惑的现象：如果同时把 Content-Type 写成 text/plain，又把 JSON 写坏，为什么看到 415 而不是 400？因为程序在类型检查就返回了，还没解析正文。

`null` 本身是合法 JSON，但不是包含 title 的对象，所以返回 422。`{"title":123}` 也一样：可以解析，但字段类型不符合约定。

### 校验要在数据改变之前

想象一个错误实现：先保存标题，再发现它只有空白，然后返回 422。页面看到失败，列表却多了无效记录。

本服务在全部检查通过后才分配 ID 和保存，所以非法请求不会改变笔记数量。之后做订单、任务和权限系统时，也要问：“失败之前有没有已经发生的修改？需要一起成功的修改如何保证？”数据库事务会回答后半个问题。

## 一次实验，看懂数据到底在哪里

如果服务尚未运行，从仓库根目录执行：

```bash
cd projects/http-playground
mvn -B -ntp test dependency:copy-dependencies
java -cp 'target/classes:target/dependency/*' com.dailystudy.day002.HttpPlayground
```

保持服务运行，另开终端执行请求。端口被占用时按 [第 02 课的启动说明](/lessons/http#启动本地实验服务) 改成 8083，后面的地址也同步改。

为了方便核对，以下从**刚启动、还没创建过笔记**的实例开始。

### 第一步：创建，再查询

```bash
curl -i 'http://127.0.0.1:8082/api/notes?limit=20'

curl -i -X POST 'http://127.0.0.1:8082/api/notes' \
  -H 'Content-Type: application/json' \
  --data '{"title":"  理解服务端状态  "}'

curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

total 从 1 变成 2；成功响应的标题被去掉了首尾空白。第一次新建通常是 ID 2，仍应以实际返回的 Location 为准读取。

### 第二步：发送非法标题，再查询

```bash
curl -i -X POST 'http://127.0.0.1:8082/api/notes' \
  -H 'Content-Type: application/json' \
  --data '{"title":"   "}'

curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

POST 返回 422，total 仍是 2。这不只是“看到错误提示”，还验证了错误请求没有写入数据。

### 第三步：刷新页面，再发送相同创建请求

刷新 `http://127.0.0.1:8082/` 实验页面，重新查询，total 仍是 2。刷新只是重新加载浏览器页面，没有重启 Java 进程。

再发送第一步的合法 POST，total 变成 3，新笔记有不同 ID。它虽然标题相同，仍是第二次创建。**重新渲染页面和重新发送写请求，效果不同。**

### 第四步：模拟失败，然后查正常接口

```bash
curl -i 'http://127.0.0.1:8082/api/demo/failure'
curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

先返回 500，再返回 200、total=3。这里 500 是教学分支，没有让服务退出，也没有清空数据。

### 第五步：停止、查询、重启

在服务终端按 Ctrl+C，然后请求：

```bash
curl -i --connect-timeout 2 --max-time 5 \
  'http://127.0.0.1:8082/api/notes?limit=20'
```

目标端口没有服务时，curl 会报告连接失败，没有服务器返回的 HTTP 状态码。再用原来的 java 命令启动服务，查询列表，total 回到 1。

原因是：**当前笔记保存在 Java 进程的内存集合里，程序启动时重新放入一条初始笔记。** 这就是接下来要学文件、数据库的理由。

::: details 这两种超时，以及超时不能证明什么
`--connect-timeout` 限制连接阶段，`--max-time` 限制整个操作。连接成功后，服务还可能在处理业务，或等待别的系统。

客户端没有及时得到结果，不等于服务没有执行。当前主动停止后的本机连接失败容易判断；真实系统出现超时，还需要日志和请求标识确认执行状态，不能盲目重发写操作。
:::

## 页面内存、服务内存和数据库，分别保存什么

“数据消失了”要先问它原来在哪：

| 保存位置 | 刷新页面后 | 重启 Java 服务后 |
|---|---|---|
| 前端组件内存 | 通常重新初始化 | 与 Java 重启没有直接关系 |
| 浏览器 localStorage | 通常仍在 | 通常仍在，但只属于该浏览器存储范围 |
| 当前 Java 实例的集合 | 仍可通过请求读到 | 丢失，重新初始化 |
| 外部数据库里已提交的记录 | 可重新查询 | 新服务进程可重新查询 |

localStorage 不是共享业务数据库；后端内存也不是可靠的持久存储。数据库的可靠性还涉及磁盘、事务、备份与恢复，后续逐层学习。

如果页面列表空了，先查 API。API 还有数据，问题可能只是页面没有重新加载；API 也为空，再调查服务和存储。**界面没显示，不能直接当作数据被删的证据。**

::: details 同一份代码启动两次，为什么数据也可能不同？
分别在 8082、8083 启动同一程序，会得到两个实例，各有自己的内存集合。在 8082 创建笔记，不会自动复制到 8083。

它们代码相同，运行状态不同。以后多实例部署时，业务记录通常放在共享数据库中，而不是只依赖某个进程的内存。

本实验重启后 ID 又从 2 开始，也说明它不是跨重启唯一的生产 ID 方案。
:::

## HTTP 无状态，为什么后端还能记住笔记

“HTTP 无状态”容易被误解成“服务器不能存东西”。其实它描述的是协议：理解当前请求，不需要 HTTP 自动记住之前交互的顺序。

```text
POST /api/notes   → 创建，得到 ID 2
GET  /api/notes/2 → 请求明确指出要读哪条笔记
```

服务读取自己保存的业务数据，完全可以。第二个请求通过 ID 表达目标，不是含糊地说“给我刚才那个”。登录时也需要明确提供或关联身份信息，例如 Cookie 或 token。

“知道笔记 ID”还不代表“有权读它”。当前实验没有登录；Spring Boot 和权限阶段会补上认证、授权和资源范围。

## 返回 JSON：Java 数据怎样变成前端数据

Java 里保存的数据不能直接穿过网络变成 JavaScript 变量，需要编码与解析：

```text
Java 数据 → 编码成 JSON → 发送正文字节
                                  ↓
JavaScript 数据 ← response.json() ← 收到正文
```

把程序里的数据转成交换格式，叫**序列化**；从交换内容解析出数据，则是相反方向的处理。

`response.json()` 读取正文并解析，不是远程调用某个 Java 方法。解析成功后，也仍要确认 HTTP 状态和字段是否符合预期。

创建响应的 201 表示这次创建成功。它不证明数据重启后仍在，也不证明任何人都能读取。不同问题要分别验证。

## 定位问题：沿着已经理解的步骤查

| 看到什么 | 下一步检查什么 |
|---|---|
| 连接失败 | 服务是否运行，地址和端口是否正确 |
| `route_not_found` | 完整 URL 是否符合契约 |
| `method_not_allowed` | GET、POST 是否选对；查看 Allow |
| `invalid_json` | Network 的 Payload 或 curl 实际正文 |
| `invalid_title` | 字段位置、类型、空白与长度 |
| 200 但页面为空 | 返回 items 是否有数据，前端是否取对字段 |
| 重启后记录没了 | 数据原来保存在内存、文件还是数据库 |

curl 成功后，浏览器失败时继续比较具体请求，尤其是 Request URL、方法、头、正文和 origin。后续加入代理与数据库后，还会用日志判断请求到达了哪一层。

::: details 三种地址别混在一起
| 地址 | 职责 |
|---|---|
| `http://localhost:5173/dailyStudy/` | 知识网站，展示课程 |
| `http://127.0.0.1:8082/` | Java 服务提供的实验页面 |
| `http://127.0.0.1:8082/api/notes` | Java 的笔记 API |

知识网站里的 `fetch('/api/notes')` 会请求知识网站所在 origin，不会自动找到 8082。当前实验在 Java 自带页面或终端进行；开发代理会在联调时专门解释。
:::

## 练习：把现象和原因连起来

### A. 判断请求停在哪一步

预测状态码、是否分配 ID：text/plain + 不完整 JSON；application/json + `null`；GET 不存在的 ID；DELETE 笔记列表；停止服务后 GET。

::: details 展开参考解释
依次是类型检查 415、字段检查 422、查询资源 404、方法检查 405、连接失败且没有 HTTP 状态码。它们都不会分配创建 ID。特别注意第一项尚未解析 JSON。
:::

### B. 推演数量

从 total=1 开始，依次合法 POST、非法 POST、查不存在的笔记、重复合法 POST、刷新页面并查询、重启并查询。total 分别是多少？

::: details 展开参考解释
依次为 2、2、2、3、3、1。只有两次合法创建增加记录；刷新与重启是不同操作。
:::

### C. 两个成功各说明什么

Maven BUILD SUCCESS 和 HTTP 201，哪个能证明重启后数据还在？你要怎么验证这个问题？

::: details 展开参考解释
都不能。前者表示这次构建命令完成，后者表示当前创建成功。要了解保存位置，并在重启后查询实际记录；本实验内存数据不会跨重启保留。
:::

### D. 找出前端的请求目标

页面在 localhost:5173，执行 `fetch('/api/notes')`。请求去哪？8082 服务启动了，为什么仍可能失败？

::: details 展开参考解释
目标是 `http://localhost:5173/api/notes`。相对路径继承当前 origin，不会自动切到 8082。需要开发代理或明确的 API 地址，并处理相应跨源配置。
:::

### E. 解释“记住数据”和“无状态”

HTTP 无状态，服务却能保存笔记；两个端口的同一份服务又能保存不同笔记。为什么没有矛盾？

::: details 展开参考解释
无状态描述协议理解请求不依赖隐含的前序交互，不禁止应用存业务数据。两个进程各自有内存，代码相同不代表状态相同；共享数据库才可能让它们读到同一份业务记录。
:::

### F. 在源码里找职责

打开 [HttpPlayground 源码](https://github.com/zzd123321/dailyStudy/blob/main/projects/http-playground/src/main/java/com/dailystudy/day002/HttpPlayground.java)，只找五件事：启动、路由、解析失败、保存、发响应。暂时不用掌握每个库 API。

::: details 展开参考解释
start 绑定并启动服务；route 根据路径和方法选择；handle 把 JSON 解析错误转成 400；createNote 在校验后分配 ID 并写 notes；sendJson 与 send 编码并发出响应。

“JSON 输入错误返回 400”不意味着所有程序异常都该返回 400。要根据失败原因区分请求错误和服务错误。
:::
