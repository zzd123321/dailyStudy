# 04 · 请求链路与服务端状态

前三课分别解决了“代码如何执行”“客户端如何发送请求”和“程序如何根据输入选择行为”。这一课把它们接起来：用户点击创建按钮后，哪段程序处理请求？数据什么时候改变？刷新、重启与再次发送请求，为什么会得到不同结果？

读完后，你应能解释一次请求从发出到响应的过程，区分不同生命周期的数据，并依据实际请求定位失败。继续使用已有 HTTP 实验服务，不需要安装数据库或学习新框架。

## 从界面操作到服务端行为

浏览器按钮不会直接调用服务器内存中的某个 Java 方法。它先构造 HTTP 请求，再由运行中的服务接收、选择处理逻辑并返回结果。

```text
用户点击按钮
  ↓
前端准备 URL、方法、请求头与正文
  ↓
客户端建立连接并发送 HTTP 请求
  ↓
服务匹配路径与方法
  ↓
解析输入 → 校验规则 → 执行业务 → 读取或修改数据
  ↓
服务把结果编码成响应
  ↓
前端读取状态与正文，更新界面
```

这是理解当前实验的模型。实际服务可能还有反向代理、认证、日志与其他依赖；不同请求也不一定经过全部阶段。例如 GET 查询条目不解析创建用的 JSON，未知路径可能直接返回 404。

## 运行中的程序，才能处理请求

第 01 课的源码、字节码与运行过程，在服务程序中仍然适用：

```text
HttpPlayground.java
  └─ Maven 编译 → target/classes 与运行依赖
       └─ java 启动 JVM → 一个运行中的 Java 进程
            └─ 绑定 127.0.0.1:8082 → 接收请求
```

编译成功只说明代码可以构建。HTTP 客户端需要的是一个正在监听目标地址与端口的服务。

本实验的 main 启动 Java HttpServer，由服务器接收请求并调度处理方法。不是每收到一个请求就重新执行 main，也不是每次点击按钮都重新编译源码。

修改服务源码后，仅刷新浏览器不会让旧进程加载新逻辑。通常需要重新编译并重启服务；框架提供的热重载在后续课程介绍。

### 四种地址不要混用

| 地址或路径 | 在这里代表什么 |
|---|---|
| `http://localhost:5173/dailyStudy/` | 本地知识网站开发服务器 |
| `http://127.0.0.1:8082/` | Java 服务提供的 HTTP 实验页面 |
| `http://127.0.0.1:8082/api/notes` | Java 服务的条目接口 |
| `projects/http-playground/src/main/java/...` | 本机源代码路径，不是 HTTP 接口 |

知识网站展示课程，Java 服务提供实验 API。在知识网站页面写 `fetch('/api/notes')`，会请求知识网站所在的 origin，不会自动切换到 8082 的服务。

本课实验在 Java 服务自带页面或终端进行。回环 IP 与 HTTP 不涉及域名解析或 TLS 握手；下一课再讨论远程 HTTPS 的前置阶段。

## 路由：先确定执行哪段逻辑

路由根据请求条件选择处理逻辑。本实验主要使用路径与方法。

```text
GET  /api/notes        → 查询列表
POST /api/notes        → 创建条目
GET  /api/notes/2      → 查询 ID 为 2 的条目
GET  /api/demo/failure → 返回教学用的 500
```

同一路径配不同方法，可能有不同含义。只比较路径而忽略方法，会把查询和创建混到一起。

下面是理解路由的伪代码，不是可直接编译的完整类：

```java
if (path.equals("/api/notes")) {
    if (method.equals("GET")) {
        // 查询列表并响应。
    } else if (method.equals("POST")) {
        // 解析、校验，再创建条目。
    } else {
        // 返回 405，并说明允许 GET、POST。
    }
} else {
    // 继续匹配其他接口；最终未匹配时返回 404。
}
```

第 03 课的 if、字符串内容比较与 return，可以帮助理解这里的选择和提前返回。Spring Boot 会用路由配置和注解表达类似职责。

### 同样的 404，可能发生在两个位置

```bash
curl -i 'http://127.0.0.1:8082/api/unknown'
curl -i 'http://127.0.0.1:8082/api/notes/999999'
```

第一条没匹配到接口，错误码是 `route_not_found`。第二条匹配了查询接口，但没有对应资源，错误码是 `note_not_found`。

HTTP 状态相同，不代表失败阶段与原因相同。诊断要同时看路径、方法和错误正文。

## 解析、校验与业务执行各自负责什么

用终端程序与 HTTP 创建接口对照：

| 职责 | 第 03 课计划器 | HTTP 创建条目 |
|---|---|---|
| 获得原始输入 | Scanner 读取一行 | 读取请求头与正文字节 |
| 解析 | parseInt / parseDouble | JSON 解析 |
| 校验 | 天数 1–7、小时有限且在范围内 | title 是非空字符串，最多 120 个 Unicode 码点 |
| 业务执行 | 计算时长与分类 | 分配 ID，保存条目 |
| 输出 | 打印报表 | 状态码、响应头与 JSON |

两者媒介不同，但都要把“能读到”“能解析”“符合规则”“执行成功”分开。

### 当前 POST 的实际检查顺序

```text
匹配 POST /api/notes
  ↓
Content-Type 是 application/json 吗？        否 → 415
  ↓
正文超过 8192 字节吗？                      是 → 413
  ↓
能解析为单个 JSON 值吗？                    否 → 400
  ↓
是对象，且 title 为字符串吗？               否 → 422
  ↓
title 去空白后非空且不超过长度上限吗？       否 → 422
  ↓
分配 ID → 写入内存 → 设置 Location → 返回 201
```

因此 text/plain 加不完整正文，会先得到 415，而不是 400。媒体类型检查通过前，本服务不尝试解析 JSON。

JSON 的 `null` 是有效 JSON，但不满足对象与 title 的规则，所以返回 422。它和计划器用 null 表示取消，是不同约定。

`{"title":123}` 也不符合契约。不能因为数字能显示成文字，就默认后端应该自动替客户端转换。

### 输入校验要在数据改变之前

当前服务通过全部检查后才分配 ID 并保存条目。先保存再检查，会让失败请求留下不应存在的数据。

更复杂的业务会涉及多次写入，例如创建订单与扣减库存，需要事务控制。当前内存实验建立顺序意识，不实现数据库事务。

单次请求的校验与客户端重试也不同：第一次写入成功但客户端没收到响应时，重复 POST 仍可能重复创建，需要后续的幂等设计。

## 数据属于哪个生命周期

数据还在不在，首先取决于保存位置，而不是页面有没有刷新。

| 数据位置 | 示例 | 生命周期与边界 |
|---|---|---|
| 一次请求的局部值 | 本次解析得到的 title | 用于这次处理，不自动成为持久数据 |
| 前端页面内存 | 组件里的列表 | 页面重新加载通常重新初始化 |
| 浏览器本地存储 | localStorage | 可跨刷新保存，不是共享后端数据库 |
| Java 服务内存 | 本实验的 notes | 当前实例可重复读取，重启重新初始化 |
| 外部持久存储 | 数据库中的已提交记录 | 可由新服务进程读取，可靠性仍依赖存储与备份设计 |

局部变量离开作用域后，无法再通过该变量访问对象；实际内存回收时机由运行时决定。这里讨论数据使用的生命周期，不要求现在研究垃圾回收。

### 刷新浏览器不会清空服务内存

重新加载页面与重启 Java 进程是不同事件。服务继续运行，创建过的条目还在，重新 GET 可以读到。

若前端列表消失，先确认页面是否重新查询、服务返回了什么。界面没显示，不足以证明服务器删除了数据。

### 重启当前服务会恢复初始数据

每次启动创建新的应用实例，其中只有 ID 1 的初始条目，nextId 从 2 开始。

所以重启后新条目可能再次得到 ID 2。这不是跨重启唯一的生产 ID 方案，而是当前内存实验的初始化规则。

### 不同实例的内存也不同

在 8082 创建条目，不代表另一份运行在 8083 的实例也有它。两份相同代码各自创建内存集合。

生产系统常用共享数据库保存业务数据，不能依赖某一个实例的内存就是全部事实。暂时不用学习负载均衡，先理解“同一份代码可以启动多个拥有不同状态的进程”。

## HTTP 无状态，不等于系统没有数据

HTTP 被称为无状态协议：理解一条请求的语义，不要求协议自动记住之前发生的请求顺序。它不禁止应用保存条目、会话或用户数据。

```text
第一次：POST 创建条目 → 服务保存数据
第二次：GET 指定 ID   → 请求明确带上资源标识
```

第二次不是靠“我刚才创建的那个”这种隐含顺序，而是通过路径 ID 指定资源。服务仍可读取此前保存的业务状态。

Cookie、Session 或 token 可携带或关联身份上下文。认证回答请求者是谁，授权决定能访问什么，不会因为使用 HTTP 就自动完成。

当前实验没有登录，知道 ID 不能作为生产系统里的权限证明。

## 响应如何回到前端

Java 程序操作内存数据，HTTP 正文发送字节，两者之间需要序列化：

```text
Java 数据 → JSON 编码 → 响应正文字节
                         ↓
                    客户端收到字节
                         ↓
             response.json() → JavaScript 数据
```

`response.json()` 是读取并解析正文，不是执行服务端方法。解析成功不保证字段符合前端预期，状态与结构仍需检查。

创建响应中的 201 表示本接口成功创建，Location 给出读取位置：

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/notes/2

{"id":2,"title":"理解请求链路"}
```

这个相对 Location 属于返回它的 Java 服务。实验里的完整读取地址是 `http://127.0.0.1:8082/api/notes/2`，不是知识网站路径。

再 GET 可核对条目能被读取，但不证明重启后仍存在，也不证明其他用户有权访问。

## 用已有服务做一次完整实验

在 Mac 的仓库根目录执行：

```bash
cd projects/http-playground
mvn -B -ntp test dependency:copy-dependencies
java -cp 'target/classes:target/dependency/*' com.dailystudy.day002.HttpPlayground
```

保持服务终端运行。8082 已被占用时，按 [第 02 课](/lessons/http#启动本地实验服务) 切换端口，后面的请求也一起修改。

另开终端。以下计数以**刚启动且还没创建条目**的实例为起点。

### 查询、创建、重新读取

```bash
curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

初始 total=1。再创建：

```bash
curl -i -X POST 'http://127.0.0.1:8082/api/notes' \
  -H 'Content-Type: application/json' \
  --data '{"title":"  理解请求链路  "}'
```

应返回 201，标题首尾空白被去掉。以实际 Location 为准读取新条目，再查列表：

```bash
curl -i 'http://127.0.0.1:8082/api/notes/2'
curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

全新实例首次创建得到 ID 2，total=2。以后不要不看响应就把 ID 当成固定值。

### 校验失败不改变条目数量

```bash
curl -i -X POST 'http://127.0.0.1:8082/api/notes' \
  -H 'Content-Type: application/json' \
  --data '{"title":"   "}'

curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

POST 返回 422，随后 total 仍为 2。同时观察错误响应和数据变化，核对处理规则。

### 重复请求不是前端重新渲染

再次发送相同的合法创建请求，会再返回 201、产生不同 ID，total=3。

刷新页面只是重新加载界面；重复 POST 是又发起一次创建业务操作，两者不能混为一谈。

### 500、停止、重启分别观察

```bash
curl -i 'http://127.0.0.1:8082/api/demo/failure'
curl -i 'http://127.0.0.1:8082/api/notes?limit=20'
```

先看到 500，再看到列表 200 且 total=3。模拟失败没有让整个服务退出或清空条目。

在服务终端按 Ctrl+C，再执行：

```bash
curl -i --connect-timeout 2 --max-time 5 \
  'http://127.0.0.1:8082/api/notes?limit=20'
```

目标端口没有服务时，应出现连接失败，没有服务端 HTTP 状态码。connect-timeout 限制建立连接阶段，max-time 限制整个操作；超时也不能被直接解释成“请求没有执行”。

重启服务再查询，total 恢复为 1。现在你同时验证了校验顺序、重复创建和内存生命周期。

## 按证据定位，而不是只猜状态码

沿链路逐层缩小范围：

| 现象 | 已知证据 | 下一步 |
|---|---|---|
| 连接失败 | 没拿到 HTTP 响应 | 检查地址、端口、进程与监听 |
| route_not_found | 请求已到达，没找到接口 | 比较完整 URL 与契约 |
| method_not_allowed | 路径已知，方法不支持 | 检查方法与 Allow |
| invalid_json | 已进入正文解析 | 看实际发送的正文 |
| invalid_title | JSON 可解析，字段不符合规则 | 检查类型、去空白与长度 |
| 200 但界面为空 | HTTP 成功不保证渲染正确 | 看 items、前端取值与渲染 |
| 重启后条目消失 | 旧数据可能只在内存 | 检查存储位置 |

curl 成功证明某个具体请求可工作。浏览器失败时，继续比较 URL、方法、头、正文、origin 与浏览器限制，不直接断定所有后端行为都正确。

真实 500 可能来自应用、数据库或其他依赖，也可能由代理返回；结合错误正文和日志判断。本实验的 demo_failure 只是专门设计的模拟分支。

## 综合练习

### A. 将现象对应到阶段

判断最早返回阶段，以及是否分配 ID：

1. POST /api/notes，text/plain，加不完整 JSON。
2. POST /api/notes，application/json，加 `null`。
3. GET /api/notes/999999。
4. DELETE /api/notes。
5. 停止服务后 GET /api/notes。

::: details 展开参考解释
1. 媒体类型检查返回 415，尚未解析，不分配 ID。
2. JSON 解析成功，结构不合规则，返回 422，不分配 ID。
3. 匹配查询接口，找不到资源，返回 404，不创建数据。
4. 方法检查返回 405，不删除数据。
5. 连接失败，没有进入服务逻辑，没有 HTTP 状态码。
:::

### B. 推演数据变化

全新实例 total=1，依次执行：合法 POST、非法 POST、查询不存在条目、重复相同合法 POST、刷新浏览器、重启服务。

预测每一步的 total，再实测核对。刷新后重新 GET，不以页面残留的旧内容作为数据证据。

::: details 展开参考解释
依次为 2、2、2、3、3、1。只有两次合法 POST 增加数据；刷新不重启服务，重启重新创建内存状态。
:::

### C. 解释两个成功为什么不同

Maven BUILD SUCCESS 与 HTTP 201 分别说明什么？能否证明条目重启后仍在？

::: details 展开参考解释
Maven 成功说明这次构建命令完成，是否测试取决于阶段。201 是当前创建请求成功。两者都不证明持久化，需要检查存储并验证重启后读取。
:::

### D. 找出前端请求目标

页面在 localhost:5173，写 `fetch('/api/notes')` 会访问哪里？为什么不能用“8082 服务已启动”证明它成功？

::: details 展开参考解释
访问 `http://localhost:5173/api/notes`，相对路径继承当前 origin，不自动切换服务。开发代理或显式跨源请求能改变链路，但需要配置；本实验用 Java 服务自带页面保持同源。
:::

### E. 状态与无状态

HTTP 无状态、服务内存保存条目、数据库持久化为什么可以同时成立？不同端口的两份程序，条目数量为什么可能不同？

::: details 展开参考解释
无状态描述协议理解请求不依赖隐含的前序交互，不禁止保存业务数据。内存属于当前实例，数据库可被不同进程共享并跨服务重启保存。相同代码各自创建内存集合，不等于相同运行状态。
:::

### F. 追踪代码职责

打开 [HttpPlayground 源码](https://github.com/zzd123321/dailyStudy/blob/main/projects/http-playground/src/main/java/com/dailystudy/day002/HttpPlayground.java)，找出以下位置，不要求掌握全部库 API：绑定与启动、匹配路径与方法、把解析异常变为 400、校验后保存、设置 Location 与 Content-Type。

::: details 展开参考解释
start 创建服务器并绑定回环地址；route 选择路径与方法；handle 捕获 JsonProcessingException 并返回 400；createNote 校验后生成 ID、写入 notes、设置 Location；sendJson 与 send 编码并发送。

不能照搬成“所有异常都应该返回 400”，错误处理要依据契约与失败原因。
:::
