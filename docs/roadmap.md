# AI 应用全栈转型学习计划

适用背景：三年前端开发经验，Java、Python 基础薄弱；每周学习四天，每天两到三小时；目标是 AI 应用全栈岗位。

本计划以每周 10 小时安排 48 个学习周，约 480 小时。另留 4–8 周用于补课、项目返工和生活中断，通常需要约 12–13 个月。长期只有每周 8 小时，可以拉长到约 15 个月；经常能投入 12 小时，也应按验收结果决定是否加速。课时是规划值，不是学会或获得工作的保证。

目标岗位以“已有前端能力 + 能独立交付业务后端 + 能交付大模型应用”为中心。Java 承担业务系统，Python 承担 AI 服务。暂不把模型预训练、分布式训练、算法研究作为就业主线。大模型算法工程师需要另一条更长、数学和训练要求更高的路线。

## 1. 终点：需要能独立完成什么

1. 把产品需求转成数据模型、接口契约、权限规则和测试场景。
2. 用 Java、Spring Boot、SQL 实现业务 API，处理校验、事务、异常、登录、资源权限和分页。
3. 用 Python、FastAPI 实现模型调用、流式输出、文档处理、检索和工具调用。
4. 知道 RAG、结构化输出、工具调用各自适用的场景，能评估效果与成本。
5. 能让系统在模型超时、服务重启、重复提交和非法输入时保持可理解的行为。
6. 能测试、部署、定位日志，清楚说明自己做了什么、为什么这样设计、还有哪些边界。

求职时如实表述“三年前端经验，具备 Java/Python 后端及 AI 应用项目实践”，不要把学习项目写成三年后端生产经验。

## 2. 学习节奏

建议固定四天，例如周二、周四、周六、周日。下面使用“第 1–4 天”表示一周的四次学习，不要求四天连续。

每次约 150 分钟：15 分钟回忆上次内容，35 分钟阅读或视频，80 分钟编码，20 分钟测试与记录。第四天可用部分编码时间做验收和复盘。从第 9 周起，在第四天安排约 30 分钟算法练习或面试表达，计入当周预算。

- 第 1 天：学习本周新概念，并完成一个最小例子。
- 第 2 天：脱离教程做练习，特别检查边界与失败情况。
- 第 3 天：把能力接入主线项目。
- 第 4 天：验收、修复、记录，再进入下周。

一个主题只保留一份主要教程和一份官方参考。视频用于建立理解，文档用于核对当前 API。遇到旧版教程，保留原理，按当前官方文档处理依赖、配置和 SDK。

每天留下：一项可运行的产出、一项真实的验证、三句话以内的学习记录。允许用 AI 解释概念、检查代码和帮助定位错误；关键业务、权限、事务和检索逻辑必须能自行讲解和修改。每周至少做一次不依赖 AI 生成整段实现的小练习。

## 3. 技术范围与项目主线

使用你已熟悉的 React 或 Vue；前端只补 AI 交互需要的流式显示、取消请求、任务状态、引用展示和错误恢复。

后端默认采用 Java 21 LTS、Maven、兼容该 JDK 的稳定 Spring Boot 版本、MyBatis、Spring Security、PostgreSQL、Flyway。按所选版本的兼容矩阵固定依赖；不要混用不同大版本的教程与配置。若目标岗位统一要求其他受支持版本，再做调整。

Python 使用与依赖兼容的受支持版本、uv 管理环境与锁文件、FastAPI、Pydantic、httpx、pytest。AI 部分先使用一个模型供应商的官方 SDK，并核对模型是否支持结构化输出、工具调用、流式输出；聊天模型和嵌入模型可以分开选择。接口格式相似，不代表功能与错误行为完全兼容。

向量检索先用 PostgreSQL + pgvector，减少基础设施数量。暂不要求 Redis、Kafka、Elasticsearch、Kubernetes 或多个向量数据库。队列、缓存和微服务框架只在真实需求出现或目标岗位明确要求时补充。

普通开发电脑加模型 API 即可推进主线，不要求购买 GPU。模型调用先设小额预算、限制输出长度、缓存适合缓存的嵌入，并使用公开或自制测试资料。

主线项目：**团队知识与任务助手**。

- V0：Java 命令行任务管理器。
- V1：用户登录、工作空间、知识条目和任务管理的 Java Web 系统。
- V2：Python 模型服务，提供摘要、信息提取、流式问答。
- V3：基于团队文档的 RAG，附引用，支持权限隔离和评估。
- V4：有限工具调用、后台文档处理、运行监控、自动化验证和部署。

Java 负责业务身份、权限、业务数据；Python 负责 AI 处理。先保持一个 Java 服务和一个 Python 服务，后台处理需要时再加 worker 进程。服务间身份应验证，用户和工作空间范围应从可信认证上下文获得，不能接受前端随意提交的 tenant_id 作为权限证明。

## 5. 48 周逐周、逐日任务

### 第 1–2 周：把已有前端知识接到服务端

**第 1 周：工具与 HTTP。**

- 第 1 天：安装 JDK、IDE 和 Maven；运行一个 Java main；复习 Git 分支与提交。不要花时间配置复杂插件。
- 第 2 天：观察浏览器网络面板中的请求方法、URL、请求头、正文和响应；用 curl 重现一次 GET 和 POST。
- 第 3 天：用 Java 写输入、判断、循环和方法的小程序，对比 TypeScript 的类型和执行方式。
- 第 4 天：画出“浏览器 → 后端 → 数据库”的请求路径，解释常见 2xx、4xx、5xx；验收工具链和小程序。

**第 2 周：接口契约与服务端状态。**

- 第 1 天：建立 DNS、TCP、TLS 的基本概念；重点理解这些环节如何影响请求失败，不深入网络协议实现。
- 第 2 天：为知识条目的创建、查询、更新、删除设计请求和响应；区分路径参数、查询参数和 JSON 正文。
- 第 3 天：理解 Cookie、Session、CORS、CSRF 的关系，写出项目登录后的身份传递方案草稿。
- 第 4 天：整理 5–8 个业务接口草稿和一份名词解释；用自己的话说明客户端校验与服务端校验为什么都需要。

验收：能定位请求的输入与输出；知道认证和授权的区别；工具链可运行。此时不用实现完整登录系统。

资料：[Java 官方学习入口](https://dev.java/learn/)、[MDN HTTP](https://developer.mozilla.org/zh-CN/docs/Web/HTTP)。

### 第 3–8 周：把 Java 学到能写、能改、能测试

**第 3 周：语法与方法。**

- 第 1 天：类型、变量、运算、控制流、数组和方法。
- 第 2 天：做任务状态转换、输入校验、统计数量等练习。
- 第 3 天：实现任务的添加、列出、完成三个命令。
- 第 4 天：手动验证空输入、非法状态和不存在的任务，修复问题。

**第 4 周：对象与接口。**

- 第 1 天：类、构造器、访问控制、接口、组合与继承；了解 record。
- 第 2 天：用不同的任务存储实现说明接口如何隔离变化。
- 第 3 天：把命令解析、业务规则、存储拆开，避免一个 main 包含所有逻辑。
- 第 4 天：解释拆分后的职责，并独立增加一个“修改标题”命令。

**第 5 周：集合与泛型。**

- 第 1 天：List、Set、Map、泛型、equals/hashCode。
- 第 2 天：练习去重、分组、查询；理解 HashMap 的使用约束和复杂度。
- 第 3 天：实现按状态筛选、任务去重、排序。
- 第 4 天：测试重复 ID、相同标题、空列表；解释为什么选当前集合。

**第 6 周：异常、文件与测试。**

- 第 1 天：异常分类、资源关闭、Path/Files；建立 Maven + JUnit 项目。
- 第 2 天：写有明确分隔规则的简单文件保存与读取；处理损坏和缺失文件。
- 第 3 天：让任务退出程序后仍能恢复；为核心业务写有意义的单元测试。
- 第 4 天：重启程序验证持久化，执行测试，区分业务错误与系统错误。

**第 7 周：常用 API 与重构。**

- 第 1 天：Lambda、Stream、时间 API、Optional 的合理使用。
- 第 2 天：用循环和 Stream 分别实现一项统计，对比可读性。
- 第 3 天：加入截止时间与过期筛选，整理命名与模块职责。
- 第 4 天：验证时区或日期边界，确保重构不改变既有行为。

**第 8 周：并发基础与阶段收尾。**

- 第 1 天：线程、共享状态、线程池、Future、超时；建立堆栈和对象生命周期的基本概念。
- 第 2 天：写一个独立的小实验，限制同时执行的任务数，观察异常与超时。
- 第 3 天：完成 CLI README、运行命令和测试；不强行把并发加入单用户 CLI。
- 第 4 天：闭卷增加一个小功能；复盘引用传递、集合、异常和资源管理。

验收：CLI 可从干净目录运行，数据能持久化；核心规则和异常输入有测试；能解释类、接口、集合、泛型和异常。复杂 JVM 调优、反射和并发框架实现留到有具体问题时。

资料：[Java 官方教程](https://dev.java/learn/)。视频可在 B 站选择一套较新的 Java 基础课程，只看语法、面向对象、集合、异常、IO、并发基础对应章节；避免同时刷多套长课。

### 第 9–12 周：数据库决定业务后端能否可靠工作

**第 9 周：关系模型与基础 SQL。**

- 第 1 天：主键、外键、非空、唯一约束、表之间的关系。
- 第 2 天：练习 SELECT、INSERT、UPDATE、DELETE。
- 第 3 天：设计用户、工作空间、成员、知识条目、任务的最小表结构。
- 第 4 天：用样例数据验证关系和约束；开始每周一题算法练习。

**第 10 周：查询与数据建模。**

- 第 1 天：JOIN、GROUP BY、聚合、子查询。
- 第 2 天：写“用户能看到的知识条目”“各工作空间未完成任务数量”等查询。
- 第 3 天：增加必要约束与排序、分页规则；理解适度规范化。
- 第 4 天：用跨工作空间数据检查查询，避免只在一组数据上验证。

**第 11 周：事务与并发。**

- 第 1 天：ACID、提交、回滚、隔离级别与常见并发异常。
- 第 2 天：用两个数据库连接观察并发更新和锁。
- 第 3 天：设计一个必须原子完成的操作，例如创建知识条目并写审计记录。
- 第 4 天：主动使中间步骤失败，验证前面的写入不会遗留。

**第 12 周：索引与 JDBC。**

- 第 1 天：B-tree、联合索引、执行计划；理解索引的读写代价。
- 第 2 天：对一个真实过滤与排序查询比较索引前后的 EXPLAIN。
- 第 3 天：用 JDBC 和参数化 SQL 访问数据库；了解连接池、SQL 注入和分页边界。
- 第 4 天：整理 SQL 脚本与运行说明，独立写几条 JOIN 和事务操作。

验收：业务关系正确；约束能阻止非法数据；能演示事务回滚；能说明一个索引为什么有效。暂不要求复杂分片和数据库内核。

资料：[SQLBolt 练习](https://sqlbolt.com/)、[PostgreSQL 官方教程](https://www.postgresql.org/docs/current/tutorial.html)。

### 第 13–20 周：完成 Java 业务系统 V1

**第 13 周：Spring Boot 与 REST。**

- 第 1 天：项目结构、依赖管理、配置、Controller、依赖注入。
- 第 2 天：实现一个最小 REST 接口，区分 DTO 与内部对象。
- 第 3 天：搭建知识条目 API 的 Controller/Service/Repository 层次。
- 第 4 天：用真实请求验证成功与失败响应。

**第 14 周：MyBatis 与持久化。**

- 第 1 天：Mapper、参数绑定、结果映射；理解 SQL 实际执行内容。
- 第 2 天：实现数据库读写和条件查询。
- 第 3 天：把知识条目 CRUD 接入 PostgreSQL。
- 第 4 天：验证不存在的记录、重复数据和参数边界。

**第 15 周：校验、异常与迁移。**

- 第 1 天：Bean Validation、统一异常处理、合适的 HTTP 状态码。
- 第 2 天：把校验规则放在正确的位置，区分格式检查与业务规则。
- 第 3 天：用 Flyway 管理 schema；实现稳定的筛选和分页。
- 第 4 天：在临时空库重建 schema，检查无效输入和分页一致性。

**第 16 周：事务与重复请求。**

- 第 1 天：Spring 事务边界、常见代理限制和回滚行为。
- 第 2 天：实现带审计记录的原子写入并测试回滚。
- 第 3 天：给容易重复提交的创建操作设计唯一约束或幂等标识。
- 第 4 天：重复请求、制造中途失败，检查数据与响应是否符合设计。

**第 17 周：身份与权限。**

- 第 1 天：Spring Security、成熟口令哈希方案、认证与授权。
- 第 2 天：先实现一种登录方案；可先选 Session + Cookie，不同时展开 JWT/OAuth/OIDC。
- 第 3 天：实现工作空间成员与资源归属检查；理解相应的 CORS/CSRF 配置。
- 第 4 天：用两个用户、两个工作空间直接请求后端，验证越权会被拒绝。

**第 18 周：自动化测试。**

- 第 1 天：区分业务单元测试、接口测试、数据库集成测试。
- 第 2 天：用 JUnit、MockMvc 测验证、权限和异常路径。
- 第 3 天：用测试数据库验证真实 SQL、约束和事务；可用 Testcontainers，勿连生产库。
- 第 4 天：让一项关键规则故意出错，确认测试会失败，再恢复代码。

**第 19 周：前后端联调。**

- 第 1 天：复用熟悉的前端框架，制定错误显示与登录状态处理。
- 第 2 天：接入登录、列表、详情和编辑界面。
- 第 3 天：处理空状态、加载、校验、分页和重复点击。
- 第 4 天：按真实用户路径操作，定位前后端契约不一致。

**第 20 周：V1 验收。**

- 第 1 天：整理 API 文档、开发启动和样例数据。
- 第 2 天：检查权限、事务、异常、配置，修复最影响使用的问题。
- 第 3 天：完成一条完整用户流程演示和关键自动化验证。
- 第 4 天：闭卷增加一个包含 SQL、权限、前端显示的小需求。

验收：用户可登录，数据可持久化，受限资源不能越权，事务失败能回滚；前端可以走完实际业务流程；能从空测试数据库启动。尚未达到这些条件，优先补齐，后面的 AI 功能顺延。

资料：[Spring Guides](https://spring.io/guides)、[Spring Boot 文档](https://docs.spring.io/spring-boot/)、[Spring Security 文档](https://docs.spring.io/spring-security/reference/)、[MyBatis 文档](https://mybatis.org/mybatis-3/)。

### 第 21–25 周：把 Python 学到能承担 AI 服务

**第 21 周：Python 语法与数据结构。**

- 第 1 天：列表、字典、集合、切片、函数、模块。
- 第 2 天：把一项 Java 数据处理逻辑改写为 Python。
- 第 3 天：学习类型标注、dataclass、异常、上下文管理器。
- 第 4 天：写并测试一个读取文本、统计与输出结果的脚本。

**第 22 周：环境与 HTTP 客户端。**

- 第 1 天：uv、虚拟环境、pyproject.toml、锁文件和环境配置。
- 第 2 天：用 httpx 调用 V1 API，处理错误状态和响应解析。
- 第 3 天：编写文本处理模块，按需安装并固定依赖。
- 第 4 天：在新的临时环境执行锁定安装，确认脚本可运行。

**第 23 周：异步与测试。**

- 第 1 天：async/await、事件循环、I/O 密集与 CPU 密集的区别。
- 第 2 天：并行请求小实验，加入超时、并发上限和取消处理。
- 第 3 天：用 pytest 测成功、错误和边界；学习可重试错误与不可重试错误。
- 第 4 天：演示慢请求和失败请求，避免无上限重试或阻塞异步接口。

**第 24 周：FastAPI。**

- 第 1 天：路由、Pydantic、依赖、配置、自动 API 文档。
- 第 2 天：实现文本处理接口和统一错误输出。
- 第 3 天：加入服务身份验证、输入长度限制和接口测试。
- 第 4 天：直接发送无效请求，检查校验与访问拒绝行为。

**第 25 周：Java 与 Python 联调。**

- 第 1 天：确定 Java 调用 Python 的协议、超时和错误映射。
- 第 2 天：传递可信用户范围与请求 ID；Python 验证调用方。
- 第 3 天：前端经 Java 调用 Python 的真实文本处理功能。
- 第 4 天：停止 Python 服务、发送非法输入，验证系统错误可理解。

验收：可运行且可测试的 Python API；依赖可重复安装；Java 可以调用，失败路径可观察。模拟模型响应可用于接口测试，但不能代替后续真实模型验证。

资料：[Python 中文教程](https://docs.python.org/zh-cn/3/tutorial/)、[uv 文档](https://docs.astral.sh/uv/)、[FastAPI 中文教程](https://fastapi.tiangolo.com/zh/tutorial/)、[pytest 入门](https://docs.pytest.org/en/stable/getting-started.html)。

### 第 26–30 周：理解并掌握模型 API

**第 26 周：模型基础与第一次调用。**

- 第 1 天：Token、上下文窗口、生成、训练与推理、temperature、幻觉。
- 第 2 天：从宏观理解 Transformer 与注意力；只补当前需要的向量、点积和概率概念。
- 第 3 天：用官方 SDK 调用一个真实模型，记录耗时与 Token 使用。
- 第 4 天：比较提示、输入长度和输出长度对结果与成本的影响。

**第 27 周：提示与结构化输出。**

- 第 1 天：任务、上下文、示例和输出约束的设计。
- 第 2 天：把自然语言任务提取为有 schema 的结构化字段。
- 第 3 天：用 Pydantic 校验模型输出，处理缺字段、拒绝和解析失败。
- 第 4 天：用至少十个不同输入测试，不靠一个漂亮示例判断效果。

**第 28 周：流式交互。**

- 第 1 天：模型流与 SSE 的事件生命周期。
- 第 2 天：实现前端增量显示、取消与失败状态。
- 第 3 天：接通 Python → Java → 浏览器的流式链路，或使用清楚鉴权的专门流式端点。
- 第 4 天：验证中断、慢响应、部分内容后报错；防止取消后继续浪费调用。

**第 29 周：只读工具调用。**

- 第 1 天：模型提出工具名和参数，程序校验、执行、回传结果的流程。
- 第 2 天：定义查询任务或知识条目的只读工具。
- 第 3 天：加入白名单、参数校验、身份范围、次数和总耗时限制。
- 第 4 天：测试错误参数、未知工具、无权限查询和循环调用。

**第 30 周：基础评估与失败处理。**

- 第 1 天：建立约二十条摘要、提取或工具查询样例，定义成功标准。
- 第 2 天：记录模型、提示版本、耗时、Token、结果与人工判定。
- 第 3 天：实现合理超时、有限重试、速率限制与错误反馈。
- 第 4 天：输出评估报告，区分模型效果问题和程序可靠性问题。

验收：真实 API 能完成选定任务；结构化输出经程序校验；流式中断可处理；非法工具与越权请求被拒绝；有多个样例的评估结果。不要用模型自评分作为唯一依据。

资料：[Hugging Face LLM Course 中文版](https://huggingface.co/learn/llm-course/zh-CN/chapter1/1)、[DeepLearning.AI 短课入口](https://www.deeplearning.ai/short-courses/)、所选供应商的当前 SDK 与功能文档。短课可选择 Prompt Engineering、Building Systems with ChatGPT API 等对应主题；旧课程代码要按当前接口适配。

### 第 31–36 周：把 RAG 做成可解释的知识库

**第 31 周：文档与嵌入。**

- 第 1 天：文本切分、Embedding、余弦相似度、召回、生成的关系。
- 第 2 天：选十到二十篇有明确答案的公开或自制文档。
- 第 3 天：按段落和标题切分，保留来源、页码或位置等元数据。
- 第 4 天：人工检查分块是否完整表达事实；记录模型和向量维度。

**第 32 周：向量检索。**

- 第 1 天：pgvector 的存储、距离、索引和基本检索。
- 第 2 天：存储嵌入，返回查询的 Top-k 块。
- 第 3 天：所有查询包含可信工作空间范围；记录文档和嵌入版本。
- 第 4 天：用已知问题核对检索结果，测试另一个工作空间不能命中。

**第 33 周：回答与引用。**

- 第 1 天：构建带来源标识的检索上下文，限制提示长度。
- 第 2 天：要求基于可见文档回答，证据不足时明确说明。
- 第 3 天：实现引用字段、后端引用校验和前端跳转原文。
- 第 4 天：检查引用内容是否真的支持答案，测试资料里没有答案的问题。

**第 34 周：文档生命周期。**

- 第 1 天：上传大小与类型、解析失败、更新、删除和重建索引。
- 第 2 天：先实现 TXT/Markdown；PDF 作为有余力时的扩展，OCR 留后。
- 第 3 天：让更新和删除影响对应的块与嵌入，避免过期结果。
- 第 4 天：测试重复上传、半途失败、删除后仍检索等问题。

**第 35 周：建立评估集。**

- 第 1 天：整理 40–60 个问题，包含可回答、不可回答、相似概念、跨文档和权限用例。
- 第 2 天：为问题标记参考答案、预期证据、可见范围；预留约十题作最终复核。
- 第 3 天：统计检索命中、答案正确、引用支持、拒答、耗时和成本。
- 第 4 天：人工分析失败类别；最终复核题不用于反复调整提示。

**第 36 周：一次有证据的优化。**

- 第 1 天：挑当前最大问题，例如分块过碎、召回不足或上下文冗余。
- 第 2 天：只改变一项：切分、检索参数、关键词召回或重排。
- 第 3 天：在相同开发题集对比优化前后，检查速度和成本的代价。
- 第 4 天：用预留题复核，写评估报告；收集十到十五份目标岗位 JD。

验收：能从文档回答并给出可核对引用；不知道时不会被强迫生成答案；权限场景不泄漏内容；更新和删除有效；报告包含失败案例与优化前后对照。小题集指标仅证明该题集上的结果，不代表生产通用效果。

资料：[pgvector](https://github.com/pgvector/pgvector)、[Full Stack Deep Learning LLM Bootcamp](https://fullstackdeeplearning.com/llm-bootcamp/)、DeepLearning.AI 的 RAG 主题短课。Bootcamp 的较早内容适合学习系统设计与评估，API 以当前官方文档为准。

### 第 37–40 周：有限 Agent 与可靠后台处理

**第 37 周：确定性工作流。**

- 第 1 天：对比固定工作流与模型自主循环的适用范围。
- 第 2 天：定义“识别意图 → 检索 → 生成草稿 → 校验 → 返回”的有限步骤。
- 第 3 天：用普通 Python 函数和明确状态实现，不先引入多 Agent。
- 第 4 天：测试步骤失败、无证据、格式错误和终止条件。

**第 38 周：后台任务。**

- 第 1 天：持久任务状态、worker、幂等、重试、恢复；理解内存后台任务的局限。
- 第 2 天：在数据库保存文档处理任务和进度，单独 worker 执行。
- 第 3 天：实现有限重试与重复领取保护，前端查询任务状态。
- 第 4 天：处理过程中停止进程，再启动验证恢复；重复任务不重复生成索引。

**第 39 周：带确认的写入工具。**

- 第 1 天：设计“根据文档生成待办”的参数 schema 和权限。
- 第 2 天：先展示草稿与变更内容，用户明确确认后调用写入接口。
- 第 3 天：在业务后端再次验证权限、状态与幂等性，记录审计。
- 第 4 天：测试伪造用户、重复确认、非法参数和模型要求额外操作。

**第 40 周：输入与成本边界。**

- 第 1 天：Prompt Injection、工具滥用、敏感内容与日志边界。
- 第 2 天：构造含“忽略规则”等指令的文档，验证内容不会获得系统权限。
- 第 3 天：限制输入、调用次数、总时间、并发和预算；保留可诊断的失败记录。
- 第 4 天：集中复核权限与危险操作用例，解释提示层和程序层各自的防护职责。

验收：工作流会终止；写入需要确认且后端独立鉴权；任务重启可恢复；有上限和审计；文档中的指令不能越过程序权限。框架中的 Agent 配置不能替代这些业务约束。

可选：先手写一个小工作流，再学习 LangGraph 如何管理状态；了解 MCP 的工具连接与协议概念。二者都不作为此阶段必须新增的工程依赖。

### 第 41–44 周：部署、观察与自动验证

**第 41 周：容器与启动。**

- 第 1 天：Docker 镜像、容器、网络、卷和 Compose。
- 第 2 天：为 Java、Python 和 worker 建立启动方式，数据库使用持久卷。
- 第 3 天：从干净开发环境启动整套服务，按顺序执行迁移与样例数据导入。
- 第 4 天：执行登录、上传、问答与引用的一条功能检查；仅“端口开着”不算通过。

**第 42 周：可部署配置。**

- 第 1 天：配置与代码分离、秘密管理、公开入口的 HTTPS 与反向代理。
- 第 2 天：配置跨域、流式转发、上传存储、数据库备份与恢复。
- 第 3 天：部署到一台可负担的主机，或完成等价的本地部署演练。
- 第 4 天：重启服务验证持久数据与迁移；公开部署时复核认证和 HTTPS。

**第 43 周：日志与性能。**

- 第 1 天：请求 ID、结构化日志、错误分类；避免默认记录敏感正文与凭据。
- 第 2 天：统计首字耗时、总耗时、错误率、Token 与检索时间。
- 第 3 天：用固定资料和小规模并发找一个瓶颈，分别考虑 SQL、检索和模型速度。
- 第 4 天：处理超时、取消和限流，记录测试负载；不要把小规模结果宣称为高并发能力。

**第 44 周：CI 与发布检查。**

- 第 1 天：在 CI 执行 Maven 验证、pytest 和必要的前端检查。
- 第 2 天：分离确定性测试、模型 mock 测试和可控的真实模型评估。
- 第 3 天：完成可重复安装、构建和启动文档；外部 API 失败不应被掩盖为测试通过。
- 第 4 天：用同一条完整功能路径验收部署；准备初版简历与岗位匹配表。

验收：他人按 README 可以启动；关键测试真实执行；公开服务使用适当身份与 HTTPS；重启不丢业务数据；请求能定位；模型成本可观察。预算不允许购买服务器时，本地 Compose 完整验证仍可展示，但明确没有真实线上运行经验。

资料：[Docker 入门](https://docs.docker.com/get-started/)、[GitHub Actions 文档](https://docs.github.com/en/actions)。

### 第 45–48 周：把能力转换成面试证据

**第 45 周：项目材料。**

- 第 1 天：整理项目 README、架构图、数据流和关键设计决策。
- 第 2 天：准备样例数据、运行命令、测试与评估报告。
- 第 3 天：录制五到八分钟演示，展示正常路径、权限拒绝和一个失败恢复场景。
- 第 4 天：完成简历项目描述，所有数字来自实际测量。

**第 46 周：Java 与数据库面试。**

- 第 1 天：集合、equals/hashCode、异常、线程池与 JVM 基本概念。
- 第 2 天：Spring DI、事务、校验、认证授权与测试。
- 第 3 天：SQL、索引、执行计划、隔离级别、连接池、幂等。
- 第 4 天：模拟追加需求，在一到两个小时内完成含数据库和权限的接口。

**第 47 周：Python、AI 与系统设计面试。**

- 第 1 天：Python 数据结构、async/await、超时、重试和 FastAPI。
- 第 2 天：RAG、Embedding、工具调用、结构化输出、评估与 Prompt Injection。
- 第 3 天：白板设计文档问答系统，说明权限、文档更新、成本和错误处理。
- 第 4 天：做一次模拟面试，记录回答不清或无法操作的内容，定向修补。

**第 48 周：投递与反馈。**

- 第 1 天：按 JD 匹配准备针对性简历，不给所有岗位同一份描述。
- 第 2 天：投递匹配 AI 应用/AI 全栈岗位，练习项目演示和现场解释。
- 第 3 天：根据反馈补最常见的短板，不临时展开新的框架体系。
- 第 4 天：制定后续四周“投递—面试—复盘—补缺”的循环计划。

算法练习：从第 9 周持续，每周一题左右，精选约三十到四十题并回做。范围为数组、哈希、双指针、滑动窗口、栈队列、二分、树遍历和基础 BFS/DFS；动态规划只做基础题。若目标公司明确重算法，另加预算，不能挤掉所有项目验证。

## 6. 四道继续条件

**第 8 周后：** 能不看教程实现一个小 Java 功能，并解释测试为何能发现错误。

**第 20 周后：** 前后端业务流程正常；权限和事务的失败场景可演示；可在空库重建。没有达到时，AI 阶段顺延。

**第 36 周后：** 有真实模型调用、有证据可核对的 RAG、有评估集、有权限测试、有失败分析。单个问答截图不足以通过。

**第 44 周后：** 环境可复现，部署流程可执行，关键路径有测试，成本与错误可观察，能讲清实现与局限。达到后可以开始针对性求职，不必等所有可选内容学完。

## 7. 项目交付清单

- 源码、依赖版本、安装与启动命令、非秘密配置示例。
- 架构图与请求链路：浏览器、Java、Python、数据库、模型供应商。
- 数据模型、权限矩阵、API 契约与最小样例数据。
- 关键测试：校验、越权、事务、幂等、服务失败、任务恢复、文档更新与删除。
- RAG 评估集与说明；至少一项有对照的改进；失败案例与成本数据。
- 可重复的部署步骤或本地演练；日志与指标查看方式。
- 五到八分钟演示；明确未做的内容与下一步改进。

写简历时，可用“针对某问题，实现某能力，在某测试条件下得到某结果”的句式。例如：“为工作空间文档构建带引用的问答流程，使用 PostgreSQL/pgvector 实现隔离检索，在自建 N 条评估样例上比较检索改进前后的命中率、耗时与 Token 成本。”N 与指标在测量前保留空白，不编造提升百分比。

## 8. 暂不列为必修的内容

Spring Cloud 全套、复杂微服务、多消息队列、Kubernetes 运维、多个 Agent 框架、向量数据库横向大全、模型预训练、分布式训练、全面微调、CUDA、全面高数与机器学习课程。

理解这些内容的定位即可。就业后或项目确有需要时，先选一个方向补深。如果想进一步往模型算法发展，可另设二到三个月起步窗口，学习线性代数、概率、机器学习、PyTorch 和模型训练实验；不要认为一个短期扩展就等于算法岗位能力。

补充资料：[动手学深度学习](https://zh.d2l.ai/)，按需阅读张量、线性代数、概率、注意力等章节。

## 9. 进度调整规则

1. 当周任务超时，先删可选扩展和 UI 美化，保留业务正确性、权限、测试和评估。
2. 连续两周没完成，缩小项目范围或拉长周期，不用把四天学习硬变成七天。
3. 已熟悉的前端和 HTTP 内容通过验收就跳过，把时间用于后端基础。
4. 第 36 周收集目标 JD，第 44 周起尝试匹配岗位；需要 MyBatis、Redis、Spring AI 等特定技能时，只补岗位反复要求的部分。
5. 学习卡住时，把问题缩成最小复现，先确认输入、预期、实际结果和日志，再查文档或求助。

推荐资料以官方入口为主。本次云环境对多数外部文档站点返回访问限制，未能逐页核验；pgvector 的 GitHub 页面已可访问。学习时请核对当前文档版本和课程示例的依赖兼容性。
